## 1. 목적과 범위

### 1.1 이 문서가 규정하는 것

`01-data-contract.md`가 **"같은 숫자를 같은 의미로"** 를 규정한다면, 이 문서는 **"그 숫자를 어떤 순서로 보여주고, 화면 사이를 어떻게 이동하며, 누가 무엇을 바꾸는가"** 를 규정한다. 구체적으로 다음을 확정한다.

1. 화면 지도 — 5개 상단 탭과 섹터 분석 4개 서브탭 각각의 **단일 책임**
2. **상태 모델** — 공유 상태의 소유자·범위·전파 규칙·초기화 시점·영속 여부 (이 문서의 핵심)
3. 워크플로별 여정 — W1/W2/W3 각각의 시작 → 판단 → 조작 → 다음 화면, 그리고 복귀 경로
4. 화면 전환 규칙 — (출발, 조작) → (도착, 이관/유지/초기화 상태) 전이표
5. 컨트롤 규약 — 각 컨트롤이 무엇을 바꾸고, 어느 범위에 적용되며, 서버 재조회를 유발하는가
6. ASCII 와이어프레임 — 컨트롤 배치, 기준일 배지, 가중 방식 표기, 커버리지 표시, 빈/오류 상태
7. 데이터 로딩·갱신 규약 — 언제 fetch하고, 무엇이 refetch를 유발하며, 로딩 중 무엇을 보여주는가
8. 시각화 규약 — 버블 크기 매핑, 색상·투명도·범례, hover, RRG 사분면 경계, 축 라벨

### 1.2 이 문서가 규정하지 않는 것

- **지표의 정의·계산식·결측 처리**: 전부 `01-data-contract.md` 소관이다. 이 문서는 참조만 한다 (예: "초과수익률 정의는 §2.2 참조").
- **화면 구조·IA 변경**: 5개 상단 탭(`market-overview` / `sector-analysis` / `stock-explorer` / `chart-grid` / `theme-analysis`)과 섹터 분석 4개 서브탭(Table / Bubble / RRG / Bump), Stock Explorer 레이아웃을 **그대로 유지**한다. 신규 화면·신규 IA는 범위 밖이다. 바뀌는 것은 **배선·상태 소유권·컨트롤 의미**뿐이다.
- **구현 방법**: 어떤 React 훅을 쓸지, 어떤 상태 라이브러리를 도입할지는 규정하지 않는다. §3의 소유권 표를 만족하면 구현은 자유다.
- **관심 섹터 모니터링(워치리스트/핀/즐겨찾기)**: 별도 SPEC으로 이관 — 이 문서는 섹터 단위 핀·즐겨찾기 어포던스를 **설계하지 않는다**. 종목 단위 워치리스트는 이미 `frontend/src/contexts/WatchlistContext.tsx`에 존재하며(§3.6), 본 설계와 충돌하지 않는다.
- **Chart Grid / Theme Analysis 내부 동작**: 상단 탭으로 존재하되, 섹터 흐름의 **종착지**로서의 진입 계약만 규정한다.

### 3.2 설계 원칙 — 세 가지 상태 종류의 분리

현행의 근본 문제는 **"공유 선택 상태"와 "화면 이동 의도"를 하나의 `crossTabParams`로 표현**한 것이다. 이 둘은 수명·소유자·소비 규칙이 전부 다르다. 세 가지로 분리한다.

| 종류 | 정의 | 수명 | 소비 규칙 |
|------|------|------|----------|
| **A. 분석 파라미터** (Analysis Params) | 모든 섹터 화면이 **같은 값을 봐야 하는** 조회 조건. 기간·시장·기준일 | 세션 지속 (탭 전환에도 유지) | 모든 화면이 읽는다. 쓰기는 지정된 컨트롤만 |
| **B. 선택 상태** (Selection) | 사용자가 "지금 이걸 보고 있다"고 지정한 대상. 선택 섹터·선택 종목 집합 | 세션 지속. 명시적 해제 시에만 소멸 | 관심 있는 화면이 읽는다. 소비해도 사라지지 않는다 |
| **C. 내비게이션 의도** (Nav Intent) | "이 탭으로 이동해서 이걸 해라"는 **1회성 주소 지정 메시지** | 1회 소비 후 소멸 | **목적지가 명시된 화면만** 소비한다 |

**[신규] 핵심 규칙 SM-0**: 섹터 선택은 **B(지속 공유 상태)** 이고, 탭 이동은 **C(주소 지정 의도)** 다. 현행처럼 하나의 채널로 둘을 겸하지 않는다. "섹터를 고르는 것"과 "섹터 분석 탭으로 가는 것"은 별개의 행위이며, 조합은 호출부가 결정한다.

### 3.4 `crossTabParams` 대체 — 주소 지정 내비게이션 의도

**[신규] 규칙 SM-1 (의도의 주소 지정)**: 내비게이션 의도는 **반드시 목적지 탭을 명시**하고, 목적지가 일치하는 소비자만 소비한다.

```
NavIntent = {
  target:  TabId          // 필수. 이 탭만 소비할 수 있다
  id:      number         // 단조 증가 시퀀스. 같은 페이로드의 재전송을 구분한다
  payload: { subTab?, stockCodes?, focusStock? }   // 목적지별 페이로드
}
```

**[신규] 규칙 SM-2 (소비 조건)**: 소비자는 다음 3조건을 **모두** 만족할 때만 처리한다.
1. `intent.target === 자신의 탭 ID`
2. `intent.id !== 자신이 마지막으로 처리한 id`
3. 자신의 탭이 현재 활성 상태 (`activeTab === intent.target`)

**[신규] 규칙 SM-3 (해제 방식)**: 소비자는 **전역 `clearCrossTabParams()`를 호출하지 않는다.** 자신의 `lastHandledId`를 갱신할 뿐이다. 이로써 ST-2(두 소비자가 서로의 메시지를 지우는 경쟁)가 구조적으로 제거된다. 전역 의도는 대상 탭이 처리했든 아니든 **다음 `navigate()` 호출 시 덮어써진다.**

**[신규] 규칙 SM-4 (섹터 선택은 의도가 아니다)**: 섹터 선택은 `SelectionContext.selectedSector`에 직접 쓴다. 내비게이션 의도의 페이로드에 `sectorName`을 실어 나르지 **않는다**. 따라서 §3.1 ST-1/ST-2/ST-3의 원인 자체가 사라진다.

**호출 조합 예시** — "트리맵에서 섹터를 클릭하면 섹터 분석 탭으로 이동한다"는 두 행위의 합성으로 표현된다.

```
onSectorClick(name):
   selection.selectSector(name)                     // B: 지속 선택
   navigate({ target: 'sector-analysis',            // C: 1회성 이동 의도
              payload: { subTab: 'table' } })
```

"순위 테이블 행 클릭"은 **선택만** 한다 (이동 없음) — ST-3의 정답이다.

```
onRowClick(name):
   selection.selectSector(name)                     // B만. navigate 호출 없음
```

### 3.5 두 화면이 충돌할 때 누가 이기는가

**[신규] 규칙 SM-5 (단일 선택 원칙)**: `selectedSector`는 앱 전체에 **하나뿐이다.** 어느 화면에서 섹터를 고르든 같은 슬롯에 쓴다. 마지막 쓰기가 이긴다.

**[신규] 규칙 SM-6 (스코프 추종 토글)**: SM-5는 다음 충돌을 낳는다 — 사용자가 Table에서 `반도체`를 선택해 상세를 보다가, Stock Explorer에서 전체 종목을 보고 싶어 칩의 `×`를 누르면 Table의 선택까지 풀린다. 이를 해소하기 위해 **`sectorScopeFollow` 불리언**을 둔다.

| 조작 | `selectedSector` | `sectorScopeFollow` | Stock Explorer가 보는 모집단 |
|------|------------------|---------------------|---------------------------|
| 어디서든 섹터 선택 | `반도체` | `true`로 강제 | 반도체 종목만 |
| Stock Explorer 칩 `×` | `반도체` **유지** | `false` | 전체 종목 |
| 다시 어디서든 섹터 선택 | 새 값 | `true` | 새 섹터 종목만 |
| Table에서 선택 해제(선택 행 재클릭) | `null` | `true` (무의미) | 전체 종목 |

이로써 "Stock Explorer의 스코프 해제"와 "섹터 선택 자체의 해제"가 분리된다. 칩 `×`는 **전역 선택을 지우지 않는다** — 사용자가 섹터 분석 탭으로 돌아가면 `반도체`가 여전히 선택되어 있다 (§4.1 W1 복귀 경로).

**[신규] 규칙 SM-7 (분석 파라미터의 단일 인스턴스)**: `market`과 `period` 토글은 **화면마다 별개 인스턴스를 두지 않는다.** 현행은 Table 툴바(`SectorAnalysis.tsx:127-151`)와 Bubble 툴바(`BubbleChart.tsx:100-145`)가 **서로 독립된 기간·시장 상태**를 가지며(`SectorAnalysis.tsx:57,59` vs `BubbleChart.tsx:28-29`), 심지어 초기값도 다르다(`m1` vs `1w`). 이는 W1을 깨뜨린다 — 같은 섹터가 Table에서는 1M 기준 3위, Bubble에서는 1W 기준 다른 위치에 있는데 사용자는 두 화면이 같은 조건이라고 믿는다. 토글은 **섹터 분석 탭 헤더에 단 한 벌** 두고, 서브탭 전환에도 유지된다.

### 3.6 범위 밖 상태와의 비충돌 확인

`WatchlistContext.tsx`는 **종목 단위**(`code` 키) 비영속 `useState` Map이다. 본 설계가 도입하는 `SelectionContext`는 **섹터 단위** `selectedSector` + 종목 단위 `selectedStocks`(Stock Explorer 로컬)를 다루며, 워치리스트와 키 공간이 겹치지 않는다. "관심 섹터 모니터링"은 §1.2대로 범위 밖이므로, `SelectionContext`에 핀/즐겨찾기 필드를 **추가하지 않는다.**

### 5.3 `selectedStocks` 초기화 규칙

**[신규] 규칙 TR-16**: 종목 체크 선택은 **모집단이 바뀌면 초기화**한다 (TR-4, TR-9, TR-12). 근거: 체크는 "이 목록에서 이것들"이라는 의미이며, 목록이 통째로 바뀐 뒤 남은 체크는 사용자가 볼 수 없는 종목을 포함한다. 현행 `StockExplorer.tsx:22`의 `selectedStocks`는 어떤 필터 변경에도 초기화되지 않아, 섹터 A에서 3개를 고른 뒤 섹터 B로 옮기면 **"3 selected"가 표시되지만 표에는 보이지 않는** 상태가 된다.

단 **Stage 필터 변경(TR-10/11)에서는 초기화하지 않는다** — Stage는 같은 섹터 모집단 안의 부분집합 뷰이며, 사용자가 Stage 2에서 2개, Stage 1에서 1개를 누적 선택하는 것이 자연스럽다.

### 6.2 시장 토글 — UI 상태에서 실제 필터로

**[신규] 규칙 CT-1**: 시장 토글은 다음을 **동시에** 바꾼다.

1. **집계 유니버스** — 섹터 구성종목이 해당 시장으로 제한된다 (`01-data-contract.md §4.2 UN-7`: 필터 → 그룹핑 → 가중치 → 집계 순서)
2. **벤치마크** — KOSPI/KOSDAQ/All 각각의 상한 적용 시총가중 집계로 전환된다 (`01-data-contract.md §6.1 BM-1`)
3. **순위** — 필터 후 유니버스로 재계산된 순위가 내려온다 (§6.3)
4. **제외 섹터 목록** — 최소 구성수 미달로 빠진 섹터가 생긴다 (`01-data-contract.md §5.4 AG-5`)

**적용 대상 화면**: Table, Bubble(섹터/종목 모두), RRG, Bump, 종목 탐색 — **전부**. 현행은 Bubble 섹터 뷰만 `market` 파라미터를 보내고(`api/bubble.ts:6-16`), RRG·Bump·종목버블·종목탐색은 보내지 않는다.

**[신규] 규칙 CT-2 (제외 섹터의 가시성)**: KOSPI 필터에서 디스플레이(4종목)·스마트폰(4종목)이 순위 대상에서 제외된다(`01-data-contract.md §4.2` 실측). 이들은 **목록에서 숨기지 않고** 표 하단의 "표본 부족으로 제외" 영역에 사유·종목수와 함께 표시한다. 사용자가 섹터의 존재 자체를 놓치면 W1이 깨진다.

**[신규] 규칙 CT-3 (토글 전환 시 선택 유지)**: 시장 전환으로 현재 `selectedSector`가 제외 대상이 되면, **선택을 지우지 않고** 상세 패널 자리에 "이 시장 필터에서는 표본 부족(n=4)으로 순위 대상에서 제외되었습니다"를 표시한다. 조용히 선택을 해제하면 사용자는 자기가 뭘 보고 있었는지 잃는다.

### 6.3 기간 토글과 순위 — 가장 눈에 띄는 결함의 해소

#### 현행 동작 (실측)

1. `handlePeriodChange`가 `sortField`를 `excess_{period}`로 바꾸고 내림차순으로 재정렬한다 (`SectorAnalysis.tsx:90-94`)
2. `sortedSectors`는 배열을 재정렬하지만 각 원소의 `rank` 필드는 손대지 않는다 (`:70-87`)
3. 표는 서버 `rank`를 그대로 렌더한다 (`SectorRankingTable.tsx:88-91`)
4. 서버 `rank`는 고정 복합점수 `0.3·1W + 0.4·1M + 0.3·3M` 기준이며(`01-data-contract.md §5.6 AG-9`), `/sectors/ranking`은 `period`도 `market`도 받지 않는다 (`backend/routers/sectors.py:43-58` — 인자 없는 `sector_ranking()`)

→ 1W로 정렬하면 Rank 열이 `1, 2, 4, 26, 3, 6, 15, …`처럼 읽힌다. **숫자와 행 순서가 서로를 반박한다.**

#### **[신규] 규칙 CT-4 (순위는 (기간, 시장)의 함수)**

`rank`는 서버가 **현재 (period, market)** 기준으로 계산해 내려준다. 기본 정렬은 `rank` 오름차순이므로, 화면 진입 시 Rank 열과 행 순서는 **항상 일치**한다.

#### **[신규] 규칙 CT-5 (복합점수는 별도 열로 보존)**

기간별 순위로 전환하면 다기간 종합 관점을 잃는다. 이를 막기 위해 **`Composite` 열을 독립 정렬 가능 열로 유지**하고, 그 헤더에 가중치를 명시한다(`복합점수 0.3·1W+0.4·1M+0.3·3M`). 사용자는 "1M 기준 1위"와 "종합 1위"를 동시에 볼 수 있다.

**명시적 트레이드오프**:

| 항목 | 이득 | 비용 |
|------|------|------|
| rank = f(period, market) | Rank 열과 행 순서가 절대 어긋나지 않는다. `rank_change`도 같은 기준으로 해석 가능해진다 | 기간을 바꿀 때마다 서버 재조회가 필요하다. `/sectors/ranking`에 `period`·`market` 파라미터 신설이 선행되어야 한다 |
| Composite 별도 열 | 다기간 종합 관점 보존 | 열이 하나 늘어 가로 폭을 먹는다. 두 순위가 크게 다를 때 "왜 다르냐"는 혼동 여지 (→ 헤더 툴팁으로 완화) |

> **확인 필요** — 이 방향은 프론트만으로 완결되지 않으며 `/sectors/ranking` 시그니처 변경을 요구한다. §12 O-1로 미결 등록.

#### **[신규] 규칙 CT-6 (다른 열로 정렬했을 때)**

사용자가 RS Avg 등 순위와 무관한 열로 정렬하면 Rank 열은 여전히 **(period, market) 기준 순위값**을 보여주며, 행 순서와 어긋난다. 이때 표 상단에 인라인 고지를 띄운다.

```
정렬: RS 평균 ↓ · Rank 열은 1M·전체 기준 순위입니다 (행 순서와 다름)   [순위순으로]
```

`[순위순으로]`는 `sortField`를 `rank`/`asc`로 되돌리는 원클릭 복귀다. 이로써 "번호와 순서가 다르다"는 상태가 **버그가 아니라 명시된 상태**가 된다.

**[신규] 규칙 CT-7**: `period` 또는 `market`이 바뀌면 `sortField`/`sortDirection`을 `rank`/`asc`로 리셋한다. 새 데이터가 온 뒤 옛 정렬을 이어가면 CT-6의 고지 상태로 곧장 진입해 사용자를 놀라게 한다.

### 6.4 순위변동 화살표

#### 현행 동작

`SectorRankingTable.tsx:44-52`의 `RankChange`는 `change > 0` → `▲n`, `< 0` → `▼n`, **그 외 전부** → `-`를 그린다. 즉 `rank_change === 0`(변동 없음)과 기준일 부재(백엔드가 0을 채운 경우)를 **구분할 수 없다.** 기준일은 `LIMIT 1 OFFSET 3`이라 실제로는 약 11일 전이다 (`01-data-contract.md §2.10`).

#### **[신규] 규칙 CT-8 (세 상태의 시각적 분리)**

`01-data-contract.md §9.1`의 3상태 구분을 화살표에도 적용한다.

| 상태 | 값 | 표시 | 색 |
|------|-----|------|-----|
| 상승 | `> 0` | `▲3` | positive |
| 하락 | `< 0` | `▼2` | negative |
| **변동 없음** | `0` | `–` (en dash) | muted |
| **기준 없음** | `null` | `신규` | muted + 툴팁 "4주 전 기준일에 순위 대상이 아니었습니다" |

#### **[신규] 규칙 CT-9 (기준일의 명시)**

응답의 `baseline_date`(`01-data-contract.md §2.10` 필수 동반 필드)를 **열 헤더에 표기**한다.

```
Δ순위 (4주 전 2026-07-14 대비)
```

이로써 사용자가 "11일 전인데 4주라고 쓰여 있다"는 상태를 **눈으로 검증**할 수 있다. 헤더에 날짜를 박는 것이 이 결함군에 대한 최선의 회귀 방지책이다.

### 6.5 Stage 필터와 분포 바 — 모집단 일치

### 8.2 **[신규] 규칙 LD-A (쿼리 키와 조회 시점)**

모든 섹터 관련 조회는 **쿼리 키** `(endpoint, market, period, asOfDate?, 화면별 추가 파라미터)`로 식별한다. `01-data-contract.md §7.2 SN-5`의 캐시 키 규약과 정렬되며, `grid_version`은 응답에 실려 오므로 값이 바뀌면 전체 캐시를 무효화한다.

| 조회 시점 | 동작 |
|----------|------|
| **탭/서브탭 활성화** | 해당 화면의 현재 쿼리 키가 캐시에 없거나 TTL 만료면 fetch. **비활성 탭은 fetch하지 않는다** (LD-1 해소) |

### 8.3 **[신규] 규칙 LD-C (로딩 vs stale-but-showing)**

| 상황 | 표시 |
|------|------|

### 9.2 버블 크기 — 면적 비례 매핑

#### 현행 결함 (실측)

```
// SectorBubbleChart.tsx:15-18
function normalizeBubbleSize(value, min, max) {
  if (max === min) return 40
  return 20 + ((value - min) / (max - min)) * 60      // 20~80
}
// :103 — symbolSize: (val) => val[2]
```

`StockBubbleChart.tsx:64-67`도 동일 선형 형태(15~70)다. ECharts `symbolSize`는 **지름**이므로 렌더 면적은 값의 **제곱**에 비례한다. 게다가 선형 정규화는 거래대금처럼 자릿수가 다른 분포에서 상위 1~2개가 스케일을 독점해 나머지가 최소 크기 근처에 뭉친다.

#### **[신규] 규칙 VZ-1 (면적 비례 + 로그 정규화)**

```
1) 로그 정규화 (거래대금은 자릿수 분포)
   u = (ln(v+1) − ln(v_min+1)) / (ln(v_max+1) − ln(v_min+1))       // u ∈ [0,1]
   v_max == v_min 이면 u = 0.5

2) 면적 비례 반지름 (면적이 u에 선형 비례)
   r = sqrt( r_min² + u × (r_max² − r_min²) )

3) ECharts symbolSize는 지름
   symbolSize = 2r
```

| 차트 | r_min | r_max | 결과 지름 범위 |
|------|-------|-------|--------------|
| 섹터 버블 (29개) | 7 | 34 | **14 – 68 px** |
| 종목 버블 (수십~수백) | 5 | 26 | **10 – 52 px** |

**왜 로그인가 (명시적 트레이드오프)**: 엄밀한 면적 비례(면적 ∝ 값)를 거래대금에 그대로 적용하면 최소 섹터가 1px 미만이 되어 **읽을 수 없다**. 로그 사전 변환으로 면적은 `log(값)`에 비례하게 되며, 이는 **크기를 정량적으로 읽을 수 없게 만든다**. 따라서 다음이 필수다.

**[신규] 규칙 VZ-2 (크기 범례 의무)**: 로그 스케일을 쓰는 이상 **크기 범례 없이는 크기 채널을 발행할 수 없다.** 차트 우하단에 3개 참조 버블을 실제 값과 함께 표시한다.

#### **[확정 2026-08-12] 참조값 = 기간별 고정 눈금 (per-period fixed ladder)** — §13 O-9 해결

데이터 적응형(최소·중앙값·최대)은 필터를 바꿀 때마다 눈금이 움직여 **크기를 기억할 수 없게** 만든다. 반면 전 기간 공통 단일 눈금은 `01-data-contract.md §10 O-10`(거래대금 창 = 기간 토글 연동)과 충돌한다 — 3M 누적 거래대금은 1W의 자릿수를 넘어서므로 하나의 사다리로는 3M 버블 대부분이 최대 눈금에 클램프된다. 두 문제를 함께 푸는 형태가 **기간별 고정 사다리**다.

| 기간 | 사다리 (최소 / 중간 / 최대) |
|------|---------------------------|
| **1W** | 100억 / 1,000억 / 1조 |
| **1M** | 500억 / 5,000억 / 5조 |
| **3M** | 1,000억 / 1조 / 10조 |

```
크기 = 거래대금 3M (로그·고정 눈금)   ·  ○ 1,000억   ◯ 1조   ◯ 10조
```

**규약**:
- 사다리 값은 **상수 테이블**로 단일 위치에 정의한다. 시장 필터·섹터 스코프가 바뀌어도 사다리는 움직이지 않는다.
- `v_min` / `v_max`는 데이터가 아니라 **해당 기간 사다리의 최소·최대**로 고정한다(VZ-1의 로그 정규화 입력).
- 사다리를 벗어난 값은 **최소/최대 크기로 클램프**한다. 클램프된 버블은 툴팁에 실제 값을 그대로 표기해 정보가 사라지지 않게 한다.
- 범례 텍스트에 **어느 기간의 거래대금인지** 반드시 병기한다(위 예의 `거래대금 3M`) — 기간에 따라 사다리가 바뀌므로 기간 표기 없이는 눈금이 모호하다.
- 사다리가 기간마다 다르므로 **기간이 다른 두 화면의 버블 크기는 서로 비교할 수 없다.** 같은 기간 안에서는 시점·필터를 넘어 비교 가능하다 — 이것이 고정 눈금을 택한 이유다.

**[신규] 규칙 VZ-3 (결측 거래대금)**: 최소 크기로 그리고 툴팁에 "거래대금 데이터 없음"을 명시한다. 0으로 치환하지 않으며, `v_min` / `v_max` 산출에도 참여시키지 않는다.

테두리 처리는 **차트별로 갈린다** (§9.1 테두리 채널 단일화):

| 차트 | 결측 거래대금 표현 |
|------|------------------|
| 섹터 버블 | 최소 크기 + **점선 테두리** (`01 §8.2`) |
| 종목 버블 | 최소 크기 + 툴팁 문구만. **테두리는 건드리지 않는다** — 종목 버블의 테두리는 Stage 전용이다 (`01 §8.7`, VZ-0) |

### 9.4 RRG 전용 규약

#### **[신규] 규칙 VZ-7 (사분면 경계의 의미 명시)**

`01-data-contract.md §2.11 RRG-1`에 따라 100은 이제 **벤치마크 대비 동일 성과**를 뜻한다. 사분면 라벨(현행 `RRGChart.tsx:192-197`의 Leading/Weakening/Lagging/Improving)에 **벤치마크 이름을 병기**한다.

```
Leading (전체 상한가중 대비 강함·개선)
```

범례 영역에 한 줄을 상설한다: `기준선 100 = 벤치마크(전체 상한가중)와 동일 성과`.

#### **[신규] 규칙 VZ-8 (축 범위 자동화)**

현행 `min:75, max:125` 하드코딩(`RRGChart.tsx:238, 246`)을 **100 중심 대칭 자동 범위**로 바꾼다.

```
half = max(5, ceil(max(|v − 100|) over 표시 중인 모든 점) × 1.1)
min = 100 − half,  max = 100 + half
```

100이 항상 정확히 화면 중앙에 오고, 실제 분산이 작을 때 점들이 한 점에 뭉치지 않는다. 최소 반폭 5는 데이터가 거의 100에 붙었을 때 과확대를 막는다.

#### **[신규] 규칙 VZ-9 (워밍업 미발행의 표시)**

`01-data-contract.md §2.11 RRG-2`는 워밍업 구간 미발행을 요구한다. 프론트는 응답의 `trail_start_date`를 스파크라인 헤더에 표기한다.


**[신규]**: 범례의 `기타` 항목에 구성 개수를 병기한다 — `기타 (7개 산업)`. 사용자가 회색 덩어리가 무엇인지 알 수 있어야 한다.

#### **[신규] 규칙 VZ-13 (hover 강조 범위)**

현행 `StockBubbleChart.tsx:159-162`의 `emphasis: { focus: 'series' }`는 한 종목에 호버하면 **다른 모든 산업명(중) 그룹을 흐리게** 만든다. 종목 하나를 보려는 조작에 화면 대부분이 반응하는 것은 과하다.

| 조작 | 강조 동작 |
|------|----------|
| 개별 버블 hover | **해당 버블만** 그림자 강조. 다른 series 블러 없음 (`focus: 'none'`) |
| **범례 항목 hover** | 해당 산업명(중) 그룹만 유지, 나머지 블러 (`focus: 'series'`는 여기에 적합) |
| 범례 항목 click | 해당 그룹 토글 (ECharts 기본, 현행 유지) |

RRG(`RRGChart.tsx:221`)와 Bump(`BumpChart.tsx:99-108`)의 `focus: 'series'`는 **선 차트에서 궤적/추이 하나를 따라가는 것이 목적**이므로 적합하다 — **유지**한다.

## 10. 오류·빈 상태 UX

`01-data-contract.md §9`의 5상태(데이터 없음 / 실제 0 / 계산 불가 / 저신뢰 / 정합성 경고)를 화면 표현으로 사상한다.

### 10.1 셀 수준 표현 (전 화면 공통)

**[신규] 규칙 ER-1**: 아래 표현은 전 화면에서 **동일**하다. 화면마다 다르게 표기하면 사용자가 상태를 학습할 수 없다.

| 상태 | 표시 | 스타일 | 툴팁 |
|------|------|--------|------|
| 데이터 없음 (`null` + `missing`) | `–` | muted 회색 | "원천 데이터에 값이 없습니다" |
| 실제 0 | `0.00%` | 일반 색 | 없음 |
| 계산 불가 (`null` + `insufficient`) | `계산 불가` | muted 이탤릭 | 사유 (예: "구성종목 4개 — 최소 5개 필요") |
| 저신뢰 (`low_confidence`) | 값 + `⚠` | 값은 일반, 배지는 amber | "커버리지 {n}% — 일부 종목 데이터 누락" |
| 정합성 경고 (`warning[]`) | 값 + `❗` | 값은 일반, 배지는 red | 경고 원문 (예: "벤치마크 허용오차 초과 6.27%p") |

**[신규] 규칙 ER-2 (금지)**: `01-data-contract.md §9.2`의 5개 금지 사항은 화면 계약이기도 하다. 특히 **결측을 `0` / `0.0%` / `50.0`으로 그리는 것을 금지**한다. 현행 `SectorRankingTable.tsx:39-42`의 `formatReturn`은 `value.toFixed(1)`을 무조건 호출하므로 `null`이 오면 런타임 오류이거나 `NaN%`를 그린다 — ER-1의 분기를 앞에 두어야 한다.
